### Project State & Context Ledger

### 1. Project Overview
* Name: Digital Closet / Style Aggregator (referred to interchangeably as "Kiran's Digital Closet")
* Objective: A personalized AI stylist aggregator that analyzes a user's existing closet items via photo upload and recommends real, purchasable matching items from partner brands — retrieval-based, not image generation. This project also serves as the Week 3 "Build Your AI Agent" submission for The Gen Academy (certification track, due Sept 16, 2026), so it must satisfy an agentic-system bar (decision-making, tool use, state, error recovery, human handoff) — not just a retrieval pipeline.
* Target Audience: Not explicitly discussed in this thread. Worth defining before further build work — even a rough persona (e.g., "budget-conscious 20s-30s shopper who wants outfit-matching without browsing multiple brand sites") would sharpen tool design and success metrics in Section 6.

### 2. Tech Stack & Environment
Languages: Python (confirmed — requests, dataclasses used in the scraper; no other language discussed).
  ### Frameworks:
- LlamaIndex — binds Pinecone vector search and Mem0 user profiles together (retrieval/indexing layer).
- LangChain + LangGraph — new addition per Week 3 requirement. LangGraph becomes the stateful control-flow layer sitting above LlamaIndex/Pinecone: it owns session state, decides which tool to call next, branches on low-confidence or failed results, and manages retries. LlamaIndex is not replaced — it stays as the retrieval mechanism the graph calls into.
- No frontend framework discussed yet.

  ### Database/Storage:
- Pinecone (Serverless) — two separate indexes/namespaces: bge-m3 for text embeddings, CLIP for image embeddings (confirmed non-interchangeable, must stay separate).
- PostgreSQL — user tables, auth data, digital closet items, via a PostgreSQL MCP server. Not yet built out.


  ### Key Architecture Decisions (confirmed):
- Embedding provider decision (Sept 2026): bge-m3 confirmed unavailable serverless on both Fireworks (Serverless: Not supported, dedicated-only) and Nebius (not in embedding catalog at all — Nebius offers bge-en-icl, bge-multilingual-gemma2, e5-mistral-7b-instruct instead, none of which are bge-m3). This is the same "not actually servable" pattern already hit with Qwen2.5-VL. Switched text embedding to Qwen3-Embedding-8B on Fireworks serverless, using its dimensions parameter to output 1024-dim vectors — preserves the existing 1024-dim bge-m3-index spec with no downstream changes. Separately, CLIP is not offered as a hosted embeddings API by either Fireworks or Nebius at all (neither platform serves image-embedding models, only text). Switched image embedding to local inference via sentence-transformers' clip-ViT-B-32 (512-dim, matches the existing clip-index spec exactly) — no external provider, no API cost, no availability risk. Both changes are swaps at the embedding-call layer only; the two-index/single-namespace/metadata-split architecture is unaffected.
- Index vs. namespace clarified (Sept 6, 2026): Two separate Pinecone indexes are mandatory — bge-m3-index (text) and clip-index (image) — because the two models produce different vector dimensionalities and non-comparable vector spaces; Pinecone enforces this at the infrastructure level (mismatched-dimension vectors can't even be upserted into the same index). This is distinct from a Pinecone namespace, which is a partition within a single index for same-dimension vectors. Within each of the two indexes, all 33,609 products live in a single default namespace — not sharded by store or category — so that one query against either index searches across all 7 brands in a single pass, which the cross-brand recommendation requirement depends on. Text and image separation is handled entirely by which index object is queried, never by namespace.
- Ingestion finalized: no LlamaIndex at ingestion. Direct script (seed_products_enriched.json → text string + image URL → bge-m3/CLIP(two separate indexes/namespaces) → Pinecone upsert), one namespace per index. A plain LangChain retriever), is scoped to the query-time retriever wrapper only — never ingestion, since the source data is already clean structured JSON with no unstructured-parsing problem to solve.
- Metadata split finalized: sizes, in_stock, fabric, and sleeve_type (when used as a stated hard preference, e.g. "full sleeve only") are Pinecone metadata filters only, never embedded as text. pattern and silhouette are folded into the embedded text only, for semantic ranking. occasion is both — filterable for hard exclusion and embedded for ranking within the filtered set.
- curated_pairs (pair:/setitem- tags) captured as metadata now at near-zero cost; Neo4j graph-hop enrichment on these edges remains a deliberate v2 deferral — the user's uploaded photo has no graph node to traverse from, so vector search does the real work regardless.
- LLM/provider decision (Sept 6, 2026): Qwen2.5-VL confirmed unavailable serverless on both Fireworks and Nebius (dedicated-only on both platforms). Switched to GLM-5.3-Flash for vision extraction, verified as accounts/fireworks/models/glm-5p3-flash on Fireworks and zai-org/GLM-5.3-Flash on Nebius. Provider order: Fireworks primary, Nebius fallback — if the Fireworks call fails to route or errors out, retry once against Nebius before surfacing a failure to the user. ### 3. Core Architecture & Rules
  ### Design Patterns: Two-part architecture:
- Offline ingestion pipeline: scrape → backfill/clean attributes → embed (Qwen3-Embedding-8B text / local CLIP image, parallel branches) → index (two Pinecone indexes, one namespace each).
- Runtime pipeline, agentic rather than fixed-sequence: photo upload → vision-tag (GLM-5.3-Flash) → dual Pinecone retrieval → orchestration (Llama-3.3-70B, builds a complementary-item query, not a similarity query) → display, wrapped in a LangGraph state machine that makes real decisions at each step (e.g., re-prompt the user on a low-confidence vision tag; broaden the query if Pinecone returns too few matches).
- Agent/tool-calling layer: search_brand_inventory (read, real dual-Pinecone), get_user_preferences (read, real hosted Mem0), remember_user_preference (write, real hosted Mem0, gated behind human-approval interrupt — added Step 5, Sept 13 2026), save_to_digital_closet (write, still a deliberate stub) — plus vision_extract_attributes (real Fireworks/Nebius GLM-5.3-Flash), build_complementary_query (real Nebius Llama-3.3-70B), rank_and_style (real Nebius Llama-3.3-70B styling note with deterministic fallback) as graph nodes. All 7 tool calls route through a shared call_with_retry() helper (remember_user_preference and save_to_digital_closet deliberately do not auto-retry, to avoid a double-write).

  ### Hard Constraints:
- No image-generation LLM — all recommendations must be real, retrievable partner-brand products.
- Text and image embeddings must be stored and queried in separate vector spaces/indexes (bge-m3 and CLIP are not interchangeable or comparable).
- Data sourcing limited to free/sanctioned methods for MVP — public Shopify /products.json endpoints preferred over paid scraping services or brand APIs that don't exist (Zara/H&M/Banana Republic have no public dev API).
- (Week 3 requirement): write actions require human approval by default. save_to_digital_closet and remember_user_preference (added Step 5) must both prompt for user confirmation before executing — both create/modify data, via the same interrupt_before gate. search_brand_inventory and get_user_preferences are reads and remain autonomous.
- Defined failure handling is required, not optional. Every tool call needs an explicit behavior for the "it broke" case (see Section 6 for the specific rule) rather than being left undefined.
- Dataset must be apparel-only — non-apparel leakage (gift cards, e-vouchers, return-service placeholder line items, styling accessories, gift/lifestyle products) is explicitly out of scope and must be excluded from BOTH the local seed JSON and the live Pinecone indexes before search_brand_inventory goes live — cleaning the JSON alone is not sufficient, since anything already upserted stays independently retrievable until deleted from the index itself. Deletion, not a metadata exclude-flag, is the chosen mechanism for known non-apparel records (see Section 4, Sept 8 audit) — a flag would add a permanent extra filter clause every query path must remember, to solve a problem already closed upstream at the source-JSON level.
- Missing-image handling (Sept 7, 2026 design decision): products with no CLIP vector, but confirmed real/in-stock apparel, are tagged in Pinecone text-index metadata as has_image_vector: False, image_missing_reason: "missing_url" | "fetch_failed" (metadata-only patch, no re-embedding). search_brand_inventory's merge logic must be "union with graceful fallback" — a text-only match must still surface on a strong semantic match, not be silently dropped because no image vector exists for that ID.
- Display rule: in_stock: false excludes a product from results entirely regardless of image status. has_image_vector: false + in-stock shows a distinct card variant (generic category silhouette icon, not a broken-image glyph, with a text description built from existing attributes standing in for the photo) rather than hiding the result. rank_and_style applies a small tie-breaking ranking penalty to text-only matches (not exclusion) and annotates each recommendation with display_mode: "photo" | "text_only" so the UI branches on one flag rather than re-deriving the logic per screen.

### 6. Agent Framework (new section — Week 3 requirement)

- One-liner: My agent helps me do upload my current closet items and search for matching casual, formal different matching suitable dresses(bottom or top or accessories) in web app(later mobile app), replacing hours of manual cross-brand browsing it takes to style an existing closet item today by browsing  all my favorite brands in one place. It extracts style attributes from an uploaded photo and retrieves real matching products on its own using 3 tools, hands off to the user before saving anything to their closet, and I'll know it works when a user can get a usable outfit recommendation in under 30 seconds that they'd actually click through to buy.
Field Fill in
- Agent goal Takes a photo of a user's closet item and returns real, purchasable matching pieces with styling advice.
- Where do people use it? Web app (frontend cards displaying recommendations with links to brand product pages).
- What steps does it take, in order?  1) Receive photo upload. 2) Vision LLM extracts JSON attributes. 3) Query both Pinecone indexes (CLIP image similarity + bge-m3 text similarity) via search_brand_inventory. 4) Fetch user profile via get_user_preferences (Mem0). 5) Orchestration LLM ranks candidates and writes styling advice. 6) Present cards to user. 7) On user request, save_to_digital_closet — pending approval.
- What can it actually do?  search_brand_inventory (read — queries Pinecone), get_user_preferences (read — queries Mem0), remember_user_preference (write — writes a stated preference to Mem0, requires human approval), save_to_digital_closet (write — requires human approval).
- What does it need to remember?  Session: current upload, extracted attributes, retrieved candidates (LangGraph state, held for the run/thread). Persistent, cross-session (real hosted Mem0, verified live Sept 13 2026 — not hand-waved): stated user style preferences (disliked colors, preferred brands, budget), written via remember_user_preference (human-approved) and read back via get_user_preferences on every future run for that user_id. Saved closet items themselves still go through save_to_digital_closet, which remains a deliberate stub — the human-approval gate is what the handout's write-action rule actually requires, not the storage backend behind it.
- What should it never do?  Never save an item to the user's digital closet without explicit confirmation. Never recommend a product without a live, retrievable product_url. Never fabricate product data not present in the Pinecone index.
- Human-in-the-loop Before save_to_digital_closet OR remember_user_preference executes (both write actions, same interrupt_before gate). User can also override/reject the vision LLM's extracted attributes before retrieval proceeds.
- What happens when something breaks? Vision LLM low-confidence output → ask user to re-upload rather than proceed. Vision provider itself unavailable/erroring (not just low-confidence — a hard failure, e.g. model deprecated or provider routing broken) → retry once against the fallback provider (Fireworks primary, Nebius fallback) before surfacing a plain-language error to the user. Pinecone returns too few matches → broaden query once, then tell the user no strong match was found rather than fail silently. Tool call errors (timeout, dead link) → retry once, then surface a plain-language message to the user.
